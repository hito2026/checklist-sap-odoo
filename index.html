1. Alcance y procesos de negocio (Input/Output)

1.1

Inputs de SAP hacia Odoo

Explicación breve: Qué datos transaccionales o maestros debe recibir Odoo desde SAP.

«¿Qué recibe Odoo desde SAP y con qué disparador?»

Ejemplo

SAP envía pedidos de venta confirmados; Odoo los recibe y continúa con facturación y entregas.

Casos de uso / escenarios

SAP manda pedidos → Odoo factura/entrega; SAP manda facturas/deudas → Odoo gestiona cobros y pagos.

1.2

Outputs de Odoo hacia SAP

Explicación breve: Qué datos o estados debe devolver Odoo a SAP.

«¿Qué envía Odoo de vuelta a SAP y cuándo?»

Ejemplo

Odoo devuelve nº de factura, nº de remito y estado de entrega por pedido.

Casos de uso / escenarios

Estado de facturación/cobranza, consumos de inventario, resultado de producción.

1.3

Dueño de cada proceso de negocio

Explicación breve: Qué sistema manda en cada proceso (venta, compra, producción, finanzas).

«¿Quién es el sistema de registro de cada proceso: SAP o Odoo?»

Ejemplo

SAP es dueño de finanzas y controlling; Odoo es dueño de la operación de venta/entrega.

Casos de uso / escenarios

Pedidos creados en SAP vs. creados en Odoo; cierre contable en SAP.

1.4

Punto de inicio y fin de cada flujo

Explicación breve: Dónde arranca y dónde termina cada integración.

«¿Cuál es el primer y el último paso de cada flujo?»

Ejemplo

Flujo pedido: inicia en SAP al confirmar y termina en Odoo al facturar.

Casos de uso / escenarios

Pedido, factura, inventario, maestro de clientes.

1.5

Procesos solo-Odoo / solo-SAP / coordinados

Explicación breve: Qué se ejecuta exclusivamente en cada lado y qué se coordina.

«¿Qué queda solo en Odoo, solo en SAP y qué se coordina entre ambos?»

Ejemplo

Producción corre solo en Odoo; controlling solo en SAP; ventas se coordinan.

Casos de uso / escenarios

Solo-Odoo (entregas), solo-SAP (contabilidad), coordinado (ventas+facturación).

2. Dirección y contrato de cada flujo

2.1

Quién inicia y quién responde

Explicación breve: Determinar el iniciador y el respondedor de cada comunicación.

«¿Qué sistema dispara cada flujo y cuál responde?»

Ejemplo

SAP inicia (push) el pedido; Odoo responde con acuse y luego con el estado.

Casos de uso / escenarios

Push de SAP, polling de Odoo, webhook de Odoo.

2.2

Retorno de estado

Explicación breve: Qué estado/nº de documento vuelve al origen.

«¿Qué confirmación necesita cada sistema para no desincronizarse?»

Ejemplo

Odoo devuelve a SAP: nº de factura, CAE (si aplica) y estado ENTREGADO.

Casos de uso / escenarios

Acuse de recepción, estado facturado/cobrado/entregado.

2.3

Payload y clave de idempotencia

Explicación breve: Campos del mensaje y clave que evita duplicados.

«¿Qué campos viajan y cuál es la clave única (nº pedido, GUID, nº documento)?»

Ejemplo

Payload de pedido con nº de pedido SAP + posición; clave idempotente = nº pedido + posición.

Casos de uso / escenarios

Reenvío por timeout no debe duplicar el pedido.

2.4

Reenvíos y duplicados

Explicación breve: Comportamiento ante reintentos y entregas repetidas.

«¿Qué pasa si el mismo mensaje llega dos veces?»

Ejemplo

El conector detecta por idempotencia y devuelve el mismo ID, sin crear un segundo registro.

Casos de uso / escenarios

Retry tras fallo de red, doble clic del usuario.

3. Volumetría, concurrencia y modalidad de comunicación

3.1

Volumen transaccional

Explicación breve: Cantidad de mensajes por período.

«¿Cuántos mensajes por hora/día/mes por flujo?»

Ejemplo

~2.000 pedidos/día, ~5.000 líneas, picos a fin de mes.

Casos de uso / escenarios

Dimensionar colas y throughput.

3.2

Picos y concurrencia

Explicación breve: Momentos de carga máxima y mensajes simultáneos.

«¿Hay picos de cierre de mes, campañas o temporada?»

Ejemplo

Cierre de mes triplica el volumen durante 3 días.

Casos de uso / escenarios

Prueba de volumen y autoescalado.

3.3

Síncrono / asíncrono / híbrido

Explicación breve: Modalidad de cada llamada.

«¿Necesita respuesta inmediata (síncrono) o acepta procesamiento diferido (asíncrono)?»

Ejemplo

Consulta de stock síncrona; alta de pedidos asíncrona vía cola.

Casos de uso / escenarios

Lookup de precio (síncrono), batch nocturno (asíncrono).

3.4

Middleware

Explicación breve: Si se usa un intermediario o integración directa.

«¿Tienen SAP PI/PO, SAP BTP/CPI, o middleware de terceros (Boomi, MuleSoft)?»

Ejemplo

Se usará SAP CPI para exponer OData y Odoo consumirá por REST.

Casos de uso / escenarios

Sin middleware (directo), con CPI, con ESB corporativo.

3.5

Colas, reintentos y batch

Explicación breve: Mecanismos de encolado y reintento.

«¿Se tolera procesamiento por lotes o hace falta near-real-time?»

Ejemplo

Reintentos con backoff exponencial y dead-letter queue para errores.

Casos de uso / escenarios

Reproceso de un lote fallido, sincronización nocturna de maestros.

Ejemplo

Controller REST /api/sap/pedido + autenticación por API key.

Casos de uso / escenarios

Recepción de pedidos, consulta de stock, envío de facturas.

Ejemplo

OAuth2 client-credentials entre Odoo y SAP CPI.

Casos de uso / escenarios

Usuario de servicio SAP, token por API key.

4.6

Rate limits y costo de API

Explicación breve: Límites de llamadas y costo por volumen.

«¿Hay límite de llamadas o costo por volumen en los servicios expuestos?»

Ejemplo

El OData de SAP admite 100 req/min por cuenta técnica.

Casos de uso / escenarios
